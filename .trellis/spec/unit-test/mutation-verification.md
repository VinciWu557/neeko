# 变异验证：证明测试真的能红

> **目的**：一份全绿的测试套件证明的是「代码满足这些断言」，**不是**「断言能抓住缺陷」。
> 变异验证是唯一能区分两者的低成本手段：故意改坏实现，看测试是否变红。

---

## 第一性原理

测试的价值是**信息量**，不是覆盖率。一个永远不会红的断言携带的信息量是零——
它和执行时间成正比，和安全感无关。

```
测试通过  ≠  测试有效
测试通过  +  改坏实现后测试变红  =  测试有效
```

全绿只能证明「当前实现满足断言」。它无法区分：

| 情况 | 全绿？ | 有保护作用？ |
| --- | --- | --- |
| 断言精确，实现了正确逻辑 | ✅ | ✅ |
| 断言太弱（`expect(x).toBeDefined()`） | ✅ | ❌ |
| 断言的路径根本没被走到 | ✅ | ❌ |
| 断言比对了同一个对象的两个引用 | ✅ | ❌ |

后三种只能靠变异发现。

---

## 操作步骤

1. **备份**：`cp file.ts /tmp/file.bak`
2. **改坏**：一次只改一处，改的是**行为**而不是格式
3. **确认改到了**：`grep` 必须命中新值。**这一步不能跳**（见下方「首次 0 红」）
4. **跑测试**：记录变红数量
5. **还原**：`cp /tmp/file.bak file.ts`，确认再次全绿
6. **0 红即调查**：不是「测试够强了」，是「要么测试有洞，要么这行是冗余代码」

---

## 首次「0 红」的两种真相

实测 8 轮变异、40 个变异体，**6 次首次报 0 红**。逐条查清后的分布：

| 真相 | 次数 | 处理 |
| --- | --- | --- |
| 变异没改到代码（字符串没匹配上） | 1 | 修变异脚本，重新验 |
| 测试用例不够刁钻（目标恰好排第一 / 断言太松） | 4 | 改用例，重新验 |
| **这行是真缺陷漏网** | 1 | 补断言，把缺陷钉住 |
| 这行是冗余分支 | 1 | 查清它何时才有效，补那条场景的测试 |

**结论：0 红不是结论，是待查信号。** 六次里只有一次是「测试本来就够强」。

### 案例一：变异没改到（假 0 红）

```python
# 想删掉 '  card.addChild(new Spacer(1))\n  card.addChild(box)'
# 实际文件里是 '  card.addChild(new Spacer(1))\n\n  card.addChild(box)'（多了空行）
# str.replace 没命中 → 文件没变 → 测试自然全绿
```

**防线**：变异后立刻 `grep` 新值。本仓库出现过两次「0 红实为变异没匹配」，两次都差点被当成「测试够强」。

### 案例二：测试用例不够刁钻（真 0 红，测试有洞）

「过滤后保留游标」的断言连续 4 次报 0 红，每次原因不同：

| 尝试 | 为什么没抓住 |
| --- | --- |
| 1 | 探针手写 `isKey` 比较原始字节，游标根本没动过——两边都是「没动」，断言相等 |
| 2 | 过滤词让目标项**恰好排第一**——「保留游标」和「重置到第 0 行」结果相同 |
| 3 | 换了词，目标项仍排第一 |
| 4 | **查出真缺陷**：`panel.list` 是构造时的字段，过滤重建列表后仍指向旧对象 |

前三次的教训是同一个：**用例必须让「正确实现」和「错误实现」给出不同答案**。构造这类用例时问一句：

> 如果我把这行删掉，这个断言会得到什么？

如果答案是「一样」，用例无效。

### 案例三：冗余分支

「删掉 `DSH_NEEKO_MAIN_SCREEN` 分支」报 0 红，因为默认值本来就是 `main`，删掉结果不变。
但它并非无用——只在「两个旧环境变量同时设置」时生效。查清后补了那条冲突场景的测试，
并顺势把优先级定成「保守的 main 赢」（此前是实现顺序的副作用）。

**冗余分支的判据**：删掉后行为不变，说明它在**当前默认值**下冗余；要找的是它生效的**输入组合**。

## 有效的变异类型

按「能暴露的缺陷类别」选，不要只做删除：

| 类型 | 例子 | 暴露什么 |
| --- | --- | --- |
| **删除** | 删掉一行 `restoreDock()` | 关键副作用缺失 |
| **反转** | `if (x) return false` → `return true` | 布尔方向错误（如「关闭时仍报 consumed」） |
| **常量漂移** | `10` → `100` | 边界值没被钉住 |
| **改回旧行为** | 新实现换回被替代的旧写法 | 重构是否真的改变了行为 |
| **换顺序** | 优先级栈两项对调 | 顺序是否有断言 |
| **去重执行** | 删掉 `[...lines]` 的副本 | 缓存/别名问题 |

**改回旧行为**是最有价值的一类：重构后全绿，但把实现换回旧写法仍然全绿 = 这次重构没有被测到。

---

## 与其他纪律的关系

- **TDD 的 Red 阶段**就是一次变异：先让测试红，再实现。合入前再验一次「改坏会红」，闭合回路。
- **覆盖率**回答「哪行被执行」，变异回答「哪行的效果被断言」。两者都要，但**变异优先级更高**——
  100% 覆盖率的套件可以一个缺陷都抓不到。
- 见 `.trellis/spec/unit-test/real-source-determinism.md`（真实源只承诺 `≥`，同样需要变异确认断言有效）。
